## 1. 비즈니스 컨텍스트 — 정본

PCS기술팀은 반도체 부대설비(스크러버·펌프·칠러) 담당 — 업무를 분해하면 별도의 작은 회사에 가깝다.

| 항목 | 값 | 비고 |
|---|---|---|
| 설비 규모 (자산등록 기준) | 약 **25만 대** [확정] | 수선 중·현재 미관리 영역 약 10만 대 포함 — 자산등록 절차상 존재 |
| 설비 규모 (운영 중) | 약 **15만 대** [확정] | 파이프라인 볼륨 산정의 기준 (→ [08 §2](08_DATA_OPS.md)) |
| 메이커 다양성 | 20개사 이상, 설비별 타입·모델 다수 | 기준정보 표준화가 어려운 구조적 이유 |

**조직 구조** — 데이터 프로덕트의 소비자이자 정의 주체:

| 조직 | 구성 | 데이터 관점 역할 |
|---|---|---|
| 운영그룹 ×4 (화성/평택/기흥/연구소) | 각각 펌프/칠러/스크러버 파트 | 현장 데이터의 생산·소비 주체. 사이트별 부분 개발로 시스템 사용 방식이 갈라진 지점 |
| 혁신그룹 (본부) | 자산/계약/정산/스탭 | 자산·정산 데이터의 기준 소유. 공식 마트의 1차 수요처 |
| 미래기술그룹 | 신규 PCS설비 검토·환경규제 대응·시스템 담당 | 이 파이프라인의 추진 주체 |

시사점: 같은 지표라도 사이트·그룹마다 산출 방식이 갈라져 있다 — 명명·정의의 단일 정본([10](10_NAMING_ORGANIZATION.md)·glossary)이 계층 설계보다 먼저인 이유.

## 2. 소스 시스템 지형과 I/F 전략

| **GEMS** | 도급업체 작업 정산 | 작업·정산 도메인 마트의 소스 후보 | [TBD] 시나리오 미정 |

소스를 그대로 신뢰할 수 없으므로 slv 표준화 계층이 소스별·사이트별 편차를 흡수한다([02](02_ARCHITECTURE.md)).

### I/F 전략 [확정: 시스템 I/F 지향]

| 선택지 | 평가 |
|---|---|

## 3. 끊어야 할 악순환

```
시스템 데이터 불신 → 업체 엑셀 의존 → 시스템 입력 등한시 → 시스템 방치 → 불신 심화 (반복)
```

- 엔지니어는 무엇이 기준인지 판단이 서지 않아, 더 관리될 것이라 여기는 업체 엑셀을 정본처럼 쓴다. 시스템 입력은 업체 자료를 옮겨 적고 Qual 증명을 하는 수준으로 전락했다.
- 소스 자체 품질 문제도 실재한다 — 자산변경 절차로 설비가 사이트를 이동했으나 소스 테이블이 갱신되지 않는 사례.

**파이프라인이 개입하는 지점** (악순환의 각 고리마다 하나):

| 고리 | 개입 | 근거 문서 |
|---|---|---|
| "무엇이 기준인지 모른다" | glossary 단일 정의 + 공식 마트(서빙 GOLD)가 유일한 소비 원천 | [02 결정 ⑥](02_ARCHITECTURE.md) · governance/ |
| "업체 엑셀이 더 정확하다" | 엑셀 로직을 인테이크로 발굴·SQL화하고 레거시 산출물과 **대사 검증** — 엑셀의 정확성을 흡수한 뒤 정본 지위를 회수 | [04](04_AS_IS_INTAKE.md) · quality/ |
| "시스템 데이터가 실제와 다르다" | 소스 품질 기준 체크는 PCS팀 역할(§4) — dbt test·대사·드리프트 감지가 어긋남을 드러낸다 | [08 §6](08_DATA_OPS.md) |
| "고쳐도 또 방치된다" | 모델 추가에 개발자 불필요(셀프서비스)라 유지 비용이 낮고, 검증 실패가 Publish를 차단해 나쁜 데이터가 유통되지 않는다 | [07](07_AUTHORING_FLOW.md) · [02](02_ARCHITECTURE.md) |

| 역할 | PCS기술팀 | IT 담당부서 |
|---|---|---|

- 특수 인력은 경계를 넘을 수 있으나 최종적으로 거버넌스를 통과해야 한다.

### 거버넌스 — 기술 게이트(현행) + 조직 승인(목표)

- **현행 [구현됨]**: 승격 게이트 = glossary 정의 확정 + schema.yml 테스트 + (이관 모델) 대사 검증 통과 → Manager 편입·Publish·OM 발행 자동 (→ [07](07_AUTHORING_FLOW.md)·[04](04_AS_IS_INTAKE.md)).
- **목표 [TBD]**: IT 영역과 PCS 도메인을 골고루 이해하는 **공동 거버넌스**가 프로덕트를 심사해 "팀 공식 마트"로 선정. 기술 게이트는 그 심사의 입장 요건이 된다. 위원회 구성·심사 기준은 조직 실체가 생길 때 governance/에 명문화한다 — 그전까지 기술 게이트가 유일한 게이트다.

## 5. 저장소 소유·제약

**제약 [확정]**: 장기 저장소로 권유받은 것은 IT부서의 고성능 Oracle. 단 이 DB는 설비 운영에 관여하므로 **리소스 사용 제한 + 저장(서빙) 용도로만** 활용해야 한다.

현행 구조([08 §1](08_DATA_OPS.md))가 이 제약을 충족하는 근거:

- 변환 연산은 **소모성 warehouse Postgres**에서 수행 — Oracle에는 연산 부하를 주지 않는다.
- Oracle은 Publish 결과(SLV+GOLD)의 **적재·서빙·이력 축적만** 담당 — "저장소로만 활용" 제약과 일치.
- Publish는 staging 적재 후 원자적 swap([08 §3](08_DATA_OPS.md)) — 쓰기 창이 짧고 예측 가능해 리소스 제한 안에서 운용 가능. 전송량 통제 손잡이(윈도 교체 전환 등)도 같은 절에 정의돼 있다.
- 1인 개발 전제의 자동화 구조(모델 추가 = SQL 1개, 나머지 자동)는 [03](03_DAG_DESIGN.md)·[07](07_AUTHORING_FLOW.md)에서 성립.

## 6. 유저 관점 가시성 — "어떤 정보가 안 오는지 보인다"

목표: 정보를 받는 입장에서 소스 > 변환 > 정보 > 유저 흐름을 바로 보고, 와야 할 정보 중 무엇이 안 오는지 알 수 있는 구조.

| 층위 | 현재 커버 | 상태 |
|---|---|---|
| 흐름이 어떻게 이어지는가 | OM 리니지 (dbt ref 그래프 + Glossary 연결) — [02 온톨로지](02_ARCHITECTURE.md) | 구현됨 |
| 데이터가 제때 왔는가 | dbt source freshness + 워터마크 점검 — [08 §7](08_DATA_OPS.md) | 구현됨 |
| 안 왔을 때 누가 아는가 | notifier 공통 모듈 → 메일·메신저 알림 — [08 §7](08_DATA_OPS.md) | 채널 연동 Phase 대기 |
| **유저가 스스로 결측을 보는가** | 미커버 — 현재는 운영자 알림 중심. 소비자용 "내 마트의 상류 상태" 뷰 없음 | **갭** → [roadmap](roadmap.md) |

갭의 방향 [기본값]: 새 도구를 만들지 않고 OM 리니지 화면 + freshness 상태를 소비자 진입점(GUIDE)으로 노출하는 것부터. 별도 대시보드는 소비자가 OM으로 부족하다고 실증될 때만.
