## 원문

### 배경 (Why)

1. 본 파이프라인의 목적은 PCS 기술팀의 데이터 활용 역량과 업무 처리 능력 향상이다.

2. [문제] 레거시 앱 UI가 제공하는 VIEW_TABLE의 신뢰도가 낮아, 엔지니어들이
   데이터를 추출한 뒤 Excel로 개별 가공한다. 그 결과 개인 판단에 의존한
   불규칙하고 검증되지 않은 데이터 프로덕트가 산재한다.

3. [문제] 엔지니어는 자신이 담당한 일부 업무에만 관여하며, 전체 비즈니스
   플로우를 설명하는 문서가 없다. 오래된 시스템이 VOC 기반으로 국소적으로
   변형되어 왔고, 과거 협의 내용은 방치되어 현재 흐름을 파악하기 어렵다.

4. [문제] 해당 문제를 인식하고 풀어나갈 전문가의 부재가 있다.

### 접근 (What)

4. [해법] 실제 업무를 담당하는 사람의 데이터 변환 로직을 출발점으로 삼아
   LND → Silver → Gold 계층을 구성한다. 이를 통해 흩어진 국지적 처리를
   Palantir 온톨로지처럼 '비즈니스 정의' 관점에서 통합해, 현재의 데이터
   흐름과 정의된 비즈니스를 조망한다.

5. [핵심 제약] 이 구조는 지속적으로 대규모 수정을 수반한다. 수정 주체는
   도메인 지식이 높은 분석가이며, 개발자 개입 없이 직접 모델(SQL, 데이터
   정의서)을 추가·수정하고 결과를 자유롭게 확인할 수 있어야 한다.
   (AI Agent 활용 포함)

### 파이프라인 설계 (How) — ※ 별도 ARCHITECTURE.md 권장

6. [분석가 자율성 확보] 5번 구조를 운영하며 겪은 불편(Airflow에서 DAG를
   직접 추가·관리하는 부담)을 해소하기 위해, dbt 의존성 그래프를 파싱하여
   Dynamic DAG를 자동 생성한다 (개발자 코드 작업 불필요).
   - Manager DAG: Model DAG 간 의존 관계 관리. 의존 순서대로 순차 Trigger,
     Model DAG 실패 시 의존 관계에 따라 복구.
   - Model DAG: 하나의 모델 데이터를 생성하는 Task 집합.

7. dbt로 모델 작성·계보 자동 생성·데이터 검증을 수행한다. SQL과 PySpark
   모델을 모두 지원하고, Partition 기반 의존성을 관리하며, 모든 엔진의 모델을
   빌드 과정을 통해 단일 의존성 그래프로 통합한다.

### 작업 방식 (Execution)

8. 실제 작업은 Claude Code Agent 기반으로 수행한다.

## 보완 원문 (2026-07-15)

> 구축 계기와 지향점을 정리한 보완 원문. 루트 `요구사항정의보완.md`의 정돈본을 그대로 편입.
> 상세 설계 반영: [11_TARGET_ARCHITECTURE.md](11_TARGET_ARCHITECTURE.md)

### 보완 1. 팀과 도메인

- PCS기술팀은 반도체 부대설비를 담당하는 팀이다.
- 반도체 제조회사 입장에서는 부대설비 영역으로 한정되지만, 담당 업무를 분해해 보면 별도의 작은 회사나 다름없다.
- 메인설비를 보조하는 스크러버, 펌프, 칠러를 관리한다. 설비 메이커사를 합하면 20곳이 넘고, 각 설비 안에서도 타입과 모델이 다양하다.
- 설비 규모는 자산등록 기준 약 25만 대. 이 중 운영 중인 설비는 약 15만 대이며, 나머지 10만 대는 수선 중이거나 현재 관리하지 않는 영역이지만 자산등록 절차상으로는 존재한다.

### 보완 2. 조직 구조

- 사이트별 운영그룹 4개: 화성 / 평택 / 기흥 / 연구소. 각 그룹 안에 펌프 / 칠러 / 스크러버 파트가 있다.
- 본부 개념의 혁신그룹: 자산 / 계약 / 정산 / 스탭.
- 미래기술그룹: 업체와 연계한 신규 PCS설비 검토, 환경규제 대응, 시스템 담당.

### 보완 3. 현재 시스템 지형

- EES: 설비 FDC 시스템 (운영)
- SMDM: 자산관리 시스템
- GEMS: 도급업체 작업 내용 정산 시스템
- EAM: 메인설비와 연계한 설치 TASK 관리
- 각 사이트와 그룹의 환경에 따라 시스템 내 부분 개발이 진행돼 왔고, 팀 단위에서는 이 영역들의 통일성이 없어 어려움이 있다.

### 보완 4. 문제의 메커니즘

- 엔지니어들은 어떤 것이 기준이고 옳은 데이터인지 판단이 서지 않아, 더 관리가 잘될 것이라 여기는 협력업체(상주 CS 담당)의 엑셀 파일을 주로 활용한다.
- 작업이든 설치현황이든 개조현황이든 업체 자료를 바탕으로 시스템에 입력하고 Qual 증명을 하는 수준이다.
- 원인: 시스템에 대한 신뢰도와 데이터 품질 관리 수준이 낮았고, 데이터 질 향상에 필요한 정보가 시스템에 바로 적용되기 어려운 부분도 있어 업체 자료를 대부분 활용했으며 시스템 입력은 등한시됐다.
- 방치된 시스템은 다시 신뢰를 잃는 악순환으로 이어진다.
- 소스 자체의 품질도 문제다. 실제 자산변경 절차에 따라 설비가 사이트를 이동했으나 소스 테이블의 데이터가 변경되지 않는 경우가 있다.

### 보완 5. 지향하는 모습

- 비즈니스의 정의와 데이터 흐름을 파악하고, 데이터 기반으로 일할 수 있는 환경으로 바꾼다.
- 엔지니어가 아이디어를 도출할 때 품질이 확보되고 표준화된 데이터를 사용한다.
- 팀 데이터 거버넌스 부서를 통해 프로덕트 형태로 인정받으면, 팀 내 공식 마트로 선정해 사용한다.

### 보완 6. 마트 구축 방법

- 현재 수준의 비즈니스 가시화가 우선이므로, 앱들의 VIEW_TABLE 쿼리를 그대로 내놓고 엑셀 전처리 과정까지 담아 마트에 녹인다.
- 마트 전환 과정에서는 도메인 표준명칭과 단어를 사용한다. 전사 표준단어가 존재하지만 PCS기술팀에서 쓰는 언어는 추가로 재정의해야 할 수 있다.
- 일부는 표준 데이터 자체가 필요할 수 있으나 아직 미흡하다. 임시 변경 후 추가 가공해야 하는 상황이 올 수 있다.
- VIEW_TABLE 쿼리와 함께 담당자 인터뷰로 프로세스 자체를 이해해야 한다. 자동화되면 좋겠지만 의도를 파악하기 어려운 점이 있어 인터뷰 형태를 고수한다.

### 보완 7. 역할 분담

- 협력 대상은 사내 IT 담당부서다. 이 부서는 설비 앱인 EES만 담당하지만 우리 팀 전담처럼 활동해 왔기에, 업무 자동화 추진과 함께 다루는 시스템 범위를 넓히려는 목적도 있다.
- PCS기술팀: 비즈니스 정의, 현재 운영상태 파악, 소스 데이터 품질 기준 체크, 표준화된 데이터 기반 신규 비즈니스용 마트 생성, 마트를 통한 업무 프로세스 추가·변경.
- IT 담당자: 위 체계를 이룬 시스템의 유지보수, PCS기술팀의 아이디어와 함께 신규 비즈니스 시스템 개발.
- 특수 인력은 역량에 따라 경계를 넘을 수 있으나, 최종적으로 거버넌스를 통과해야 한다.
- 거버넌스는 IT 영역과 PCS 도메인 영역을 골고루 이해하도록 공동 구성하는 것이 목적이다.

### 보완 8. 제약 조건

- 시스템 개발은 현재 1인이 진행하고 있으며, 많은 사례를 볼 때 사람이 많이 필요하지 않은 자동화된 구조를 가져가야 한다.
- 저장소는 서버 다운 시 관리를 위해 종량제 또는 IT부서의 DB 사용을 권유받았고, 고성능 Oracle DB다. 다만 이 DB는 설비 운영에 관여하는 DB라 활용이 조심스럽고, 리소스 활용에 제한을 두고 저장소로만 활용하라고 전달받았다.
- 소스 데이터 I/F 선택지: DataLake 카탈로그로 받는 방법과 시스템 I/F로 요청해 받는 방법이 있다. 현재는 시스템 I/F를 지향한다. Lake가 불안정하다는 것이 가장 큰 단점이다.

### 보완 9. 원하는 최종 형태

- 소스 시스템의 테이블을 그대로 받되, 소스마다 적재 주기가 다르므로 의존성을 자동으로 체크해 변환 과정이 연쇄적으로 일어나야 한다.
- 이 흐름을 바탕으로 Task들이 어떻게 이어지는지 볼 수 있어야 한다.
- 정보를 받는 입장에서 소스 > 변환 > 정보 > 유저의 흐름을 바로 볼 수 있고, 나에게 와야 할 정보 중 어떤 것이 안 오는지 보이는 구조를 만들고 싶다.
