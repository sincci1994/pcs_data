# 08. 데이터 운영 정책 — 볼륨·보존·지연·드리프트·옵저버빌리티

> 정책 확정 수준을 구분해 표기한다: **[확정]** 사용자 결정 / **[기본값]** 설계 기본값(반증 시 교체) / **[TBD]** 사내 확인 필요.

## 1. 저장 책임 분리 [확정]

| 저장소 | 역할 | 보존 |
|---|---|---|
| 운영 Oracle (소스) | 원본 장기 보관 | **5년** |
| warehouse Postgres | **변환 연산 자원 전용** — 작업 윈도(rolling window)만 보유 | 윈도 밖 파티션 drop |
| 서빙 DB (운영 DB 또는 별도 DB) | GOLD 산출물 적재·이력 축적 | 서빙 DB 측 정책 (5년 협의 → roadmap) |

warehouse에 데이터가 무한 축적되어 publish·스캔이 선형 증가하는 구조 자체를 배제한다.
warehouse는 언제든 소스에서 재적재 가능한 **소모성 작업 공간**이다.

## 2. 볼륨 산정 워크시트

```
5분 grain 일 유입량 = 설비 수 × 설비당 센서 수 × 288 버킷/일
warehouse 상주량   = 일 유입량 × 작업 윈도 일수 × 행 크기
```

| 입력 | 값 | 상태 |
|---|---|---|
| 설비 수 | 15만 대 | [확정] (전 fleet 기준) |
| 시나리오 대상 설비 범위 | 전체 vs 초기 부분집합 | **[TBD] 1순위** — 상주량의 1차 입력 |
| 설비당 Utility 센서 수 | 수십 개 | [TBD] 실측 |
| 일 유입량 (전체 가정) | 15만 × 수십 × 288 ≈ **4억~13억 행/일** | 추정 |
| 작업 윈도 | lookback 24h + 재동기화 윈도 N일 + 여유 | [기본값] — §4에서 N 확정 시 산출 |
| 기준정보 | 연 45만 건 수준 | 무시 가능 |

- 이 유입량 규모에서는 **일 range 파티셔닝 + incremental 모델이 선택이 아니라 필수**다 (5분 grain 경로: lnd, slv 5분 표준화).
- 보존 만료 = **파티션 drop만** — row DELETE 금지 (bloat·vacuum 비용).
- 작업 윈도 기준으로도 일 유입 처리(적재+변환)가 Postgres 단일 노드로 감당 불가로 **실측**되면, 그 시점이 [adr/0003](adr/0003-defer-pyspark-multi-engine.md)(PySpark 보류) 재검토 트리거다.

## 3. Publish 정책 (02 결정 ②의 정밀화)

| 프로덕트 볼륨 | 방식 |
|---|---|
| 소규모 마트 (기준정보·차원류) | 전량 교체 |
| 대규모 (설비×일 grain 등) | **윈도 교체** — 최근 N일 delete+insert, 과거분 불변 |

**원자성 불변조건**: staging 적재 → 단일 트랜잭션 swap(또는 트랜잭션 내 교체). 소비자는 항상 완전한 직전 스냅샷 또는 완전한 신규 스냅샷만 본다. 실패 시 이전 상태 보존 (TRUNCATE 후 INSERT 금지).

## 4. 지연 도착 데이터 [확정: 2단 방어]

1. **1차 — lookback 24h**: 매 추출이 워터마크−24h부터 재조회, 겹침 구간은 delete-before-insert 멱등 재적재 (→ platform/CLAUDE.md 규칙 1·2).
2. **2차 — 주기 재동기화 DAG**: 최근 N일 [기본값: 7일, 지연 실측 후 조정] 윈도의 구간별 건수를 소스 vs LND 대사 → 갭 발견 시 **해당 윈도만** 재적재. 대사 쿼리는 소스 부하를 고려해 윈도·주기 제한 [기본값: 주 1회].
3. **지연 도착률 메트릭**: lookback 경계 밖에서 재동기화가 회수한 건수를 기록 — lookback·N 튜닝의 근거 (quality/ 소유).

## 5. 결측 5분 버킷 [기본값: 0 취급]

- **일 합산 지표에서 0 취급은 결측 제외와 수학적으로 동일하다** (결측 행은 합산에 기여하지 않음) — 별도 채움 처리 불요.
- 실질 차이는 **평균류 지표의 분모**에서만 발생: 경과 버킷 수(0 취급) vs 수신 버킷 수(제외). → `CurrentAvgUsage` 분모 정의(glossary)로 위임.
- 결측률 기반 정교화(설비×일 결측률 산출, 지표 신뢰도 플래그)는 규모(15만 설비)상 지금 하지 않는다 → [roadmap](roadmap.md).

## 6. 스키마 드리프트 감지

[07](07_AUTHORING_FLOW.md)의 "소스 변경은 SLV에서 흡수"는 **대응 절차**다 — 여기는 **감지 메커니즘**:

1. **Extract pre-flight 계약 체크**: 적재 전 소스 딕셔너리(ALL_TAB_COLUMNS 등)를 기대 스키마와 대조 — 불일치 시 **fail-fast + 알림**. 조용한 드리프트(컬럼 추가·타입 변경이 티 안 나게 흘러들어오는 것) 금지.
2. **보조**: OpenMetadata ingestion의 스키마 변경 감지·이력.
3. 감지 → 알림 → 사람이 sources.yml·SLV 수정(07 절차) → 하류 자동 재정의.

## 7. 옵저버빌리티

| 항목 | 설계 |
|---|---|
| freshness | dbt source freshness(워터마크 기준) + 주기 점검. **주의: Airflow 3.x는 SLA 기능이 제거됨** — Airflow SLA에 의존하지 말 것, 자체 freshness 점검(+후속 Deadline Alerts 검토 → roadmap) |
| 알림 | **notifier 공통 모듈 1개** = 콜백 단일 진입점. 사내 메일 + 메신저 **API 어댑터** [확정: 두 채널 존재, 연동 Phase 3]. on_failure·freshness 위반·드리프트 감지·재동기화 갭을 전부 이 모듈로 통합 — 개별 DAG에서 채널 API 직접 호출 금지 |
| 메트릭 | 지연 도착률·재동기화 대사 결과·결측률 — quality/ 소유, ctl 스키마 기록 |
| 백필 | Manager DAG에 logical date를 파라미터로 전파 → 해당 날짜의 Model DAG 재실행. 백필 윈도 적재는 delete-before-insert 멱등이므로 중복 없음. 절차는 Manager 단위로만 수행 (Model 개별 백필은 의존성 누락 위험 — 예외 시 하류 clear 동반) |
