00풀려는 문제

같은 지표를 사람마다 다른 쿼리로 뽑으면 숫자가 갈립니다.

"이번 달 MQL이 몇 개냐"에 대시보드와 분석 노트가 다른 답을 내는 순간, 보는 사람은 둘 다 못 믿게 됩니다. 근태·인원·비용 같은 핵심 지표일수록 치명적입니다.

Metric Store는 지표의 정의(무엇을·어떤 기준으로·어떤 단위로 집계할지)를 YAML 파일 하나에 유일하게 두고, 그 정의로부터 SQL을 자동 생성해 매일 계산·적재합니다. 누구나 같은 정의의 숫자를 봅니다 — SSOT(Single Source of Truth) 원칙입니다.

01핵심 컨셉 3가지

엔지니어가 먼저 잡아야 할 세 가지 멘탈 모델.

SSOT

사람은 YAML만 만진다

지표 정의는 res/ 아래 YAML이 유일한 소스. SQL·테이블·Airflow Task는 전부 코드가 자동 생성합니다. 손으로 쓴 SQL은 없습니다.

DECLARATIVE

선언형 → 컴파일

"무엇을 계산할지"만 선언하면, Loader→Planner→Builder가 실행 계획과 SQL 문자열로 컴파일합니다. 계산 순서도 참조 관계에서 자동 도출.

IDEMPOTENT

지우고 다시 넣기

모든 적재는 DELETE 후 INSERT. 같은 날짜를 몇 번 돌려도 결과가 중복되지 않고 항상 동일합니다 (멱등성).

02아키텍처 — YAML이 SQL이 되기까지

YAML을 읽어 SQL로 바꾸고 Airflow Task로 연결하는 과정은 5개 처리 단계로 이뤄집니다. 단계 사이에 오가는 데이터는 ExecutionPlan 하나로 표현됩니다.

1
res/*.yaml

YAML 정의 — 사람이 수정하는 유일한 대상

sources/ (원본 테이블·컬럼) · metrics/ (지표 계산식·축·표시정보) · dimensions.yaml · extend_attributes.yaml · domains.yaml

2
YamlMetadataLoader

Loader — Load → Lookup → Validate

YAML을 모델로 읽고(from_yaml), 조회용 색인을 만들고(alias/파생축/암호화/카테고리), 모델 간 규칙을 검증합니다. 잘못된 정의는 여기서 걸립니다.

3
MetricStorePlanner → ExecutionPlan

Planner — 무엇을·어떤 순서로 계산할지 결정

time_unit별 그룹화 + 참조관계 위상정렬(depth) + 비용 기반 배치 분배 + chunk 수 산출을 결정적으로 수행. 결과는 값이 안 바뀌는(frozen) ExecutionPlan 객체.

4
Source / Atomic / Derived / Extend / Catalog SqlBuilder

SqlBuilder — Plan 좌표대로 SQL 문자열 생성

단위별 Builder가 중간 조회 SQL, 지표×축 집계 SQL(UNION ALL), 파생/기간비교 SQL을 만듭니다. SqlUploader가 이걸 S3에 업로드 (실행 인자 길이 제한 회피).

5
MetricStoreTaskGenerator → Spark → Iceberg

TaskGenerator — Airflow Task로 실체화 & 연결

build_all → wire_dependencies → wire_downstream. Plan의 unit/edge를 Task 단위 의존성으로 연결하고, Spark가 SQL을 실행해 insight_product.metric_store_hist에 적재합니다.

핵심 계약(contract) = ExecutionPlan. 4종 실행 단위(AtomicUnit / DerivedUnit / ExtendAtomicUnit / ExtendDerivedUnit)와 2종 기간비교 연결(cross-extend edge), chunk 크기를 담습니다. Planner 이후 모든 단계가 이 한 객체만 보고 동작합니다.

모듈 지도

모듈역할
YamlMetadataLoaderYAML → 모델 로드 + 조회 색인 + cross-model 검증
MetricStorePlannerloader + time_unit + 분배정책 → ExecutionPlan (결정적)
ExecutionPlan단계 간 유일한 데이터 계약 (frozen dataclass)
*SqlBuilderSource / Atomic / Derived / Extend / Catalog SQL 생성
MetricStoreSqlUploaderPlan 좌표대로 SQL 빌드 → S3 업로드
MetricStoreTaskGeneratorPlan → Airflow Task 생성 + 의존성 연결
kafka_export_builder각 적재 DAG 안의 kafka_upsert Task 그룹 빌더
metric_cli.py검증·조회·미리보기 도구 (validate/list/show/waves)

03지표 3유형 — YAML의 type이 곧 유형

지표는 만드는 방식에 따라 세 가지로 나뉩니다. Planner가 유형별로 다른 실행 단위를 만듭니다.

ATOMIC

기본 집계

원본 테이블에서 직접 계산
  • 컬럼을 SUM/COUNT/AVG 등으로 집계
  • 부서별·유저별·전사 등 여러 축으로 동시 집계
  • 조건 필터(condition) 가능
DERIVED

파생 지표

이미 계산된 지표들을 조합
  • 다른 지표 키를 쓴 계산식 (A / B)
  • same-dim(같은 축) / rollup(상위 축 합산) / broadcast(전사값 붙이기)
  • 참조 관계로 계산 순서 자동 결정
EXTEND

기간 비교

적재된 지표에 비교값을 덧붙임
  • 전기 대비(PREV) · 이동평균(LAST) · 전년(YOY)
  • extend_attributes만 지정하면 자동 계산
  • 원값과 다른 attribute_type으로 저장

예시로 보는 세 유형

# ATOMIC — 원본 src_user_work 에서 직접 집계
- key: WORKING_HOURS
  type: ATOMIC
  source: src_user_work
  formula: "SUM(total_working_minutes) / 60.0"
  dimensions: [ [department_id], [department_id, user_id], [customer_id] ]
  extend_attributes: [ LAST4_AVG, LAST4_AVG_DIFF ]   # ← EXTEND 자동 부착

# DERIVED — 이미 계산된 두 지표를 같은 축에서 나눔 (same-dim)
- key: WORKING_HOURS_AVG
  type: DERIVED
  formula: "WORKING_HOURS / WORKING_USER_COUNT"   # 인당 평균 근무시간
  dimensions: [ [department_id], [customer_id] ]

# DERIVED · broadcast — 전사 평균을 각 부서에 붙여 "전사 대비 차이"
- key: AGE_AVG_TOTAL_DIFF
  type: DERIVED
  formula: "AGE_AVG - AGE_AVG_TOTAL"
  cross_dimensions:
    - source: [customer_id]                # 전사 레벨
      targets: [ [direct_department_id] ]
      metrics: [ { key: AGE_AVG, alias: AGE_AVG_TOTAL } ]
축 처리(same-dim / rollup / broadcast / 구성비)를 틀리면 빌드는 통과해도 값이 조용히 어긋납니다. 특히 창 함수의 PARTITION BY에서 customer_id를 빠뜨리면 여러 고객사가 섞여 합산·순위됩니다. 패턴 결정 절차는 docs/PATTERNS.md 참고.

04동작 플로우 — 두 개의 시간대

Metric Store를 이해하는 핵심: 파이프라인은 DAG parse time과 Runtime에서 하는 일이 다릅니다.

DAG PARSE TIME

계획을 세운다 (모든 워커가 반복 실행)

Airflow가 DAG 파일을 파싱할 때마다 실행됩니다. SQL을 만들지도, 데이터를 건드리지도 않습니다. Task 그래프의 모양만 결정합니다.

  1. Loader가 YAML을 읽어 검증
  2. Planner가 ExecutionPlan 산출 (depth·배치·chunk)
  3. TaskGenerator가 Task를 만들고 의존성을 wire
RUNTIME (DAG run)

실제로 계산한다 (하루 1회)

스케줄이 돌 때 실행됩니다. 여기서 SQL이 생성·업로드되고 Spark가 실제로 계산·적재합니다.

  1. gen_sql: Uploader가 모든 SQL을 빌드해 S3 업로드
  2. atomic → derived(depth순) → extend Task가 Spark 실행
  3. kafka_upsert + clean_sql 병렬 마무리

Runtime Task 그래프

start
  → gen_sql                     # SqlUploader: 모든 SQL 빌드 → S3
  → atomic_{source}            # 소스당 1 Task (소스캐시 + 그룹 UNION ALL → write)
  → derived_batch_{idx}        # depth_0, depth_1 ... depth_K 순서 (참조 순서)
  → extend_atomic_{source}     # atomic 종료 직후
    extend_derived_batch_{d}_{i} # 해당 derived 배치 종료 직후
  → [ kafka_upsert , clean_sql ]  # leaf 이후 2분기 병렬
  → end
TaskGroup은 화면상 시각적 묶음일 뿐, 그룹 간 의존성은 없습니다. 모든 연결이 개별 Task 단위로 명시돼 있어(예: atomic_{source} → derived_batch_{idx}), 같은 depth의 배치 중 일부가 먼저 끝나면 뒤 Task가 나머지를 기다리지 않고 진행됩니다.

05멱등 적재 — DELETE 범위가 충돌을 막는다

모든 Task는 "해당 범위를 지우고 다시 넣는(DELETE + INSERT)" 방식. 지우는 범위를 metric_key + attribute_type으로 쪼개 Task 간 충돌을 원천 차단합니다.

단계작업 단위DELETE 범위
ATOMIC 소스당 1 Task atomic_{source} metric_key IN (...) + attribute_type='VALUE'
DERIVED depth 안 배치당 1 Task derived_batch_{idx} metric_key IN (...) + attribute_type='VALUE'
EXTEND 소스/배치당 1 Task extend_* metric_key IN (...) + attribute_type != 'VALUE'

→ 원값(VALUE)과 기간비교값(PREV1_DIFF 등)이 attribute_type으로 분리돼 ATOMIC/DERIVED Task와 EXTEND Task가 같은 metric_key라도 서로 다른 행을 지웁니다. 테이블은 PARTITIONED BY (part_date, time_unit, metric_key)라 파티션 단위로도 격리됩니다.

06결과 — 모든 지표가 한 테이블에

모든 지표가 insight_product.metric_store_hist 하나에 통합 적재됩니다. 한 행 = "어떤 지표를, 어떤 축으로, 언제, 얼마".

컬럼설명예시
base_date기준 일자 (주간이면 그 주의 시작일)2025-01-06
customer_id고객사 ID — 모든 지표는 고객사 단위12345
metric_group_key지표 그룹working_hours
metric_key지표 키WORKING_HOURS
dimension_name_key분석 축 이름department_id
dimension_value_key분석 축 값100
dimension_map축 조합 전체 map{department_id:100}
encrypted_dimension_mapdimension_map JSON을 암호화한 문자열—
attribute_type값의 종류VALUE, LAST4_AVG, PREV1_DIFF
value계산 결과42.50
source_table_name원본 소스 테이블timetracking_mart.src_user_work
id비즈니스 키 해시 (증분·변경 감지용)—

PARTITIONED BY (part_date, time_unit, metric_key)

조회 예시

-- 부서별 주간 근무시간 (한 고객사)
SELECT dimension_value_key AS department_id, value AS working_hours
FROM metric_store_hist
WHERE metric_key = 'WORKING_HOURS'
  AND customer_id = 12345            -- 빠뜨리면 여러 고객사가 섞임
  AND dimension_name_key = 'department_id'
  AND attribute_type = 'VALUE'       -- 원값
  AND time_unit = 'W'
  AND base_date = '2025-01-06'

-- 최근 4주 평균 대비 증감 (EXTEND)
SELECT dimension_value_key, value AS diff_from_avg
FROM metric_store_hist
WHERE metric_key = 'WORKING_HOURS'
  AND attribute_type = 'LAST4_AVG_DIFF'
  AND time_unit = 'W'

07DAG 구성

적재 4개(W/M/Q/Y) + 유지보수·카탈로그·축매핑·초기적재.

DAGSchedule단위역할
mart_metric_store_weekly_6h_30m_v130 6 * * *W주간 적재 + kafka
mart_metric_store_monthly_6h_30m_v130 6 * * *M월간 적재 + kafka
mart_metric_store_quarterly_6h_30m_v130 6 * * *Q분기 적재 + kafka
mart_metric_store_yearly_6h_30m_v130 6 * * *Y연간 적재 + kafka
..._hist_maintenance_7h_30m_v130 7 * * *—4 적재 DAG의 end 대기 후 관측통계 집계 + OPTIMIZE + VACUUM
mart_metric_store_catalog_7h0 7 * * *—YAML 변경 감지 → 카탈로그 동기화 + Kafka
..._dimension_value_mapping_7h0 7 * * *—축 값 매핑 스냅샷 + Kafka
export_metric_store_migration수동—초기 적재/재적재용 전체 스냅샷 Kafka 전송
유지보수(관측통계 + OPTIMIZE + VACUUM)를 별도 DAG로 분리한 이유: 4개 적재 DAG와 같은 테이블에 동시 커밋하면 Iceberg commit 충돌이 나기 때문. 적재 DAG들의 end를 ExternalTaskSensor로 기다린 뒤 07:30에 1회 실행합니다.

08새 지표 추가 흐름

엔지니어/분석가가 지표 하나를 추가할 때. 사람이 만지는 건 YAML과 CLI뿐입니다.

1

원본 소스 확인

res/sources/에 쓸 테이블이 있으면 통과. 없으면 _sample.yaml 복사해 소스 정의 추가 (grain·columns·joins).

2

계산 패턴 판단

docs/PATTERNS.md의 결정 절차로 ATOMIC/DERIVED·축 처리·formula 모양을 정함.

3

지표 정의 작성

res/metrics/에 key·type·formula·time_units·cast_type·dimensions·semantic 작성.

4

카탈로그 등록 (신규 축일 때만)

새 분석 축·기간비교 속성이면 dimensions.yaml/extend_attributes.yaml에 등록. 기존 것만 쓰면 생략.

5

검증

metric_cli.py validate로 오류 확인, show로 실제 생성 SQL을 눈으로 검토, waves로 계산 순서 확인.

# 검증·미리보기 CLI
python metric_cli.py validate --metric WORKING_HOURS   # 메타/컬럼/참조/문법 검증
python metric_cli.py show     --metric WORKING_HOURS   # 생성될 실제 SQL 확인
python metric_cli.py waves    --group working_hours     # DERIVED 계산 순서(depth)
