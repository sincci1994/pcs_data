01전체 지도

왼쪽의 메트릭 스토어는 코드를 실행하는 시스템, 가운데 데이터 웨어하우스는 데이터가 실제로 쌓이는 물리 공간, 오른쪽은 소비처입니다. 메트릭 스토어는 DW의 마트를 참조해 계산하고, 결과를 metric_store 물리 테이블로 적재합니다.

02두 개의 축 — 물리 vs 논리

아키텍처를 이해하는 첫 갈림길: "이건 데이터가 쌓이는 곳인가, 지표를 선언하는 곳인가".

물리적 DW

데이터가 실제로 쌓이는 공간

ODS → Source(src·dim) → 소비(fact) 로 이어지는 레이어드 아키텍처. 각 테이블은 SQL DML로 만들어져 스키마에 물리적으로 존재합니다. 표준(네이밍·타입·KST·삭제 플래그)은 데이터마트표준화가이드.md 가 SSOT.

논리적 지표 관리

지표를 선언하면 자동 계산되는 시스템

메트릭 스토어. 사람은 YAML(시맨틱 레이어)만 쓰고, 엔진이 그 위 DW 마트를 참조해 SQL을 생성·실행, metric_store_hist 로 적재합니다. 상세는 메트릭 스토어 오버뷰 참고.

03DW 3레이어

원천에서 소비까지, 데이터는 세 레이어를 거치며 점점 "질문에 답할 수 있는 형태"가 됩니다.

레이어목적스키마 예시
ODS 원천 시스템(RDB·API)을 변환 없이 1:1 복제. 스키마·컬럼명·타입이 원천과 그대로 대응. 원천의 기술적 부채(모호한 컬럼명·비정규화)가 그대로 존재. core_ods timetracking_ods fins_ods goal_ods
Source ODS의 부채를 해소하고 전사 표준으로 정제·통합한 준비된 데이터(Prepared Data). 복잡한 집계는 최소화하고 기초 클렌징 + 비즈니스 단위 통합에 집중. src_*(사건·행위) / dim_*(엔티티 마스터). core_mart.dim_* fins_mart.src_* timetracking_mart.dim_*
소비 비즈니스 질문에 직접 답하는 집계·지표 테이블. BI·리포트·ML Feature 등 목적별 구성. fact_*(집계) + 메트릭 스토어가 적재하는 metric_store_*. core_mart.fact_* bi_mart.* finance_mart.*
소스 레이어 패턴 요약: ODS → dim · ODS → src · src + src → src. 이 레이어에서 "한 행이 엔티티냐 사건이냐"를 먼저 정하는 게 핵심입니다.

04src vs dim 판별 기준

가로형/세로형이 아니라 "한 행이 무엇을 의미하는가"로 판별합니다.

질문DIM (디멘션)SRC (소스)
한 행이 무엇인가지속하는 엔티티 1개 (회사·사람·카드·목표)발생한 사건 1건 (제출·전환·거래·업데이트)
같은 엔티티에서 반복되나아니오 (1행 = 1엔티티)예 (1엔티티 = 다행)
측정치(SUM/AVG 할 수치)를 갖나없음 (기술 속성 위주)있음 (_amount, _minutes 등)
조인 방향남이 나를 FK로 참조내가 dim을 FK로 참조
빠른 판별: 측정치를 들고 dim들을 FK로 참조하면 SRC, 남들이 나를 조인 기준으로 쓰면 DIM.

프로세스·이벤트가 섞였을 때 (dim 흡수 vs src 분리)

dim 에 흡수 (3개 모두 충족)

  • 엔티티당 ~1회 발생 (accumulating snapshot이 1:1)
  • 이벤트별 이력·재진입·velocity 분석 불필요
  • 측정치 없음 — 상태/시점 스냅샷뿐

src 로 분리 (하나라도 깨지면)

분리 트리거는 cardinality가 아니라 "sub-entity 이벤트 이력(전환·재진입·velocity) 수요가 있느냐". 프로세스가 1개여도 단계 전환이 여럿이면 transition grain의 src가 필요할 수 있음.

함정. 원천이 last_* 최신 스냅샷 컬럼만 갖고 실제 전환 이벤트 로그가 없으면, 그걸 unpivot 해 src로 만들어도 정보량은 그대로이고 "이벤트 로그인 척하는 비단조 스냅샷"이 되어 오용을 부릅니다. 진짜 transition src는 SCD 스냅샷(_hist)을 diff 하는 등 이벤트 원천이 있을 때만 만듭니다.

05소스 레이어 생성 패턴 5

원천 형태와 결과물(엔티티/사건)의 조합으로 다섯 패턴이 나옵니다.

#패턴핵심 가공사례
1ODS → DIM
단일 원천 디멘션		 리네이밍 · 타입 캐스팅 / ENUM 인코딩 · 불리언 플래그 · KST 변환 dim_customer_work_form, dim_spending_category, dim_user_education
2ODS + ODS → DIM
보조 속성 결합		 CTE 사전 집계(COUNT·COLLECT_SET) · LEFT JOIN 보강 · Self JOIN 계층 판별 dim_spending_card, dim_objective
3ODS → SRC
단일 이벤트 표준화		 JSON 파싱(GET_JSON_OBJECT) · before/after 변경 감지 플래그 · 파생 계산 src_objective_progress_record
4ODS + ODS → SRC
다중 통합 이벤트		 다중 LEFT JOIN · COALESCE 체인 병합 · 소스 레이어 내 src/dim 참조(DAG 의존) · 버전 통합(v1/v3) src_spending, src_user_work
5DIM + DIM → DIM
조합 디멘션(관계 스냅샷)		 유효기간 기반 시점 조인 · ${start_date} 일별 스냅샷 · ARRAY 계층 병합(SCD Type 2) dim_department_user_position_hist
 
# 소비 레이어 참조 (패턴 4) — 소스 레이어 내 다른 테이블을 CTE로 참조 (DAG 의존성 필요)
WITH evidence AS (
  SELECT spending_id, category_name
  FROM fins_mart.src_spending_evidence
  WHERE evidence_status NOT IN ('CANCELED')
)
SELECT s.id AS spending_id, s.customer_id, s.amount AS spending_amount,
  COALESCE(cd.merchant_name, crd.merchant_name, tid.supplier_merchant_name, ed.merchant_name) AS merchant_name,
  evidence.category_name  -- 소스 레이어 참조 컬럼
FROM fins_ods.spending AS s
LEFT JOIN fins_ods.spending_card_detail AS cd ON s.id = cd.spending_id
LEFT JOIN evidence ON s.id = evidence.spending_id

06컬럼 네이밍 & 데이터 표준

컬럼명은 도메인 용어 정의 문서가 SSOT. 아래는 마트에서 특히 자주 쓰이는 표준입니다.

PK / FK 네이밍

구분패턴예시
PK{엔티티_단수}_idspending_id, objective_id, card_id
FK참조 대상 PK명 그대로customer_id, user_id, department_id
Self FK{관계설명}_{엔티티}_idparent_objective_id, parent_department_id
SK (대리키){엔티티}_sk (MD5 해시)department_sk = MD5(CONCAT_WS('||', ...))
배열 FK{엔티티}_id_list / {엔티티}_listparticipant_user_list, all_parent_department_list

컬럼 접미사 표준

_type — ENUM 분류값 _status — 상태값 _amount — 금액/수량 _count — 집계 수 _percent / _rate — 비율 _minutes — 시간(분) _depth / _level — 계층 깊이 _date — DATE _at — TIMESTAMP _list — ARRAY _json_list / _json — JSON 원본 _encrypted — 암호화 컬럼

시스템 메타 컬럼 & KST 규약

컬럼의미
db_created_at원천 DB 생성 시각 (ODS 원본)
db_updated_at원천 DB 수정 시각 (ODS 원본)
created_atKST 변환 생성 시각
updated_atKST 변환 수정 시각 (COALESCE)
deleted_atKST 변환 삭제 시각
dw_updated_atDW 적재 시각 (KST)
part_date파티션 키 (일별 스냅샷 테이블)

KST 변환 규약

-- 원천 UTC → KST
FROM_UTC_TIMESTAMP(created_at, 'Asia/Seoul')
FROM_UTC_TIMESTAMP(COALESCE(updated_at, created_at), 'Asia/Seoul')

-- DW 적재 시각 (KST = UTC+9)
CURRENT_TIMESTAMP + INTERVAL '9' HOUR

-- 소프트 삭제 플래그
IF(deleted_at IS NOT NULL, TRUE, FALSE) AS is_deleted

07메트릭 스토어의 위치 — 참조하고, 되적재한다

메트릭 스토어는 DW 옆에 붙는 논리 레이어 + 실행 엔진. DW 마트를 소스로 읽어(참조), 지표를 계산해 DW 소비 레이어에 물리 테이블로 되적재(적재)합니다.

⇠ 참조 (읽기)

시맨틱 레이어가 마트를 소스로 선언

YAML res/sources/ 에 어떤 src_*·dim_*·fact_* 를 읽을지 선언합니다. 즉 DW 소스/소비 레이어가 메트릭 스토어의 입력입니다. 그래서 마트의 그레인·네이밍 표준이 지표 정확도로 그대로 이어집니다.

적재 → (쓰기)

엔진이 metric_store 테이블 생성

Loader→Planner→Builder→TaskGenerator 가 YAML을 SQL로 컴파일해 Spark로 실행, insight_product.metric_store_hist (DW 소비 레이어)에 DELETE+INSERT 멱등 적재합니다. 카탈로그·Kafka 전송까지 자동.

결과적으로 metric_store_* 는 fact_* 와 나란히 소비 레이어의 한 시민입니다. 차이는 "사람이 SQL로 만든 집계 마트(fact)" vs "YAML 선언에서 엔진이 자동 생성한 지표 마트(metric_store)". 메트릭 스토어 내부 동작은 → 메트릭 스토어 오버뷰.

08종합 흐름 — 원천에서 소비까지

한 데이터 포인트가 원천에서 대시보드까지 도달하는 전체 경로.

[원천 RDB/API]
     │  (변환 없이 복제)
     ▼
ODS  core_ods · timetracking_ods · fins_ods · goal_ods
     │  (리네이밍 · 타입 · KST · 삭제 플래그 · 통합)  ← 5가지 생성 패턴
     ▼
Source  src_*(사건) · dim_*(엔티티)          ┐
     │  (집계 · 파생)                            │  ⇠ 메트릭 스토어 시맨틱 레이어가
     ▼                                           │     이 마트들을 "소스"로 선언 (참조)
소비  fact_*(집계 마트)                        │
       metric_store_*(엔진이 적재한 지표) ◀──────┘  적재 (YAML→SQL→Spark→멱등 INSERT)
     │
     ▼
Downstream  BI 대시보드(Metabase) · 자동 리포트/Slack · 애드혹 SQL
표준이 왜 중요한가. 소스 레이어의 그레인·네이밍이 흔들리면 그 위의 fact·metric_store가 모두 흔들립니다. src/dim 판별과 네이밍 표준은 단순 규칙이 아니라 상위 지표 정확도의 토대입니다.
