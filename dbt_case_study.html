01왜 — 끊어야 할 악순환

시작은 기술이 아니라 신뢰의 문제였습니다. 시스템 데이터를 믿지 못하니 각자 엑셀을 만들고, 시스템 입력은 소홀해지고, 시스템은 더 방치되어 다시 불신이 깊어졌습니다.

① 못 믿는 원천

레거시 앱이 제공하는 VIEW_TABLE의 신뢰도가 낮아, 엔지니어들이 데이터를 직접 뽑아 쓰기 시작했습니다.

② 검증 안 된 산출물

추출한 데이터를 각자 Excel로 가공 — 개인 판단에 의존한 불규칙하고 검증되지 않은 데이터 프로덕트가 산재했습니다.

③ 사라진 전체 그림

각자 담당 업무에만 관여하고, 전체 비즈니스 흐름을 설명하는 문서가 없어 현재 흐름조차 파악하기 어려웠습니다.

목표는 각 고리를 하나씩 끊는 것. "무엇이 기준인지 모른다"는 단일 정의 + 공식 마트로, "엑셀이 더 정확하다"는 엑셀 로직을 흡수·검증한 뒤 정본 회수로, "고쳐도 또 방치된다"는 검증 실패 시 나쁜 데이터 유통 차단으로 개입합니다.

02무엇이 흩어져 있었나

같은 지표를 여러 사람이 각자의 엑셀 함수로 계산했습니다. 계산 방법도, 기준도 사람마다 달라 "무엇이 맞는 값인가"를 아무도 단언할 수 없는 상태였습니다.

흩어진 정의 — 회계 기간의 예

"이번 회계월 실적"을 뽑을 때조차, 삼성 회계달력(매월 16일 경계) 계산이 사람·파일마다 조금씩 다른 CASE 식으로 복사·변형되어 있었습니다.

엑셀·파이썬에 갇힌 로직

정산 기타지원금 산출은 8개 비용 항목을 행으로 펼치는(melt) 개인 파이썬 스크립트였습니다. 하드코딩된 접속정보와 행 단위 업서트 등, 팀이 함께 쓰기 어려운 형태였습니다.

이 로직들은 버려야 할 대상이 아니라 흡수해야 할 자산이었습니다. 실제 업무를 담당한 사람의 변환 논리 그 자체가 비즈니스의 정의였기 때문입니다 — 그래서 "규칙은 그대로, 형태만 표준으로" 옮겼습니다.

03어떻게 풀었나 — 3계층으로 모으기

흩어진 로직을 brz → slv → gld 세 계층에 순서대로 담았습니다. 원본을 그대로 보존하고 → 깨끗하게 정리하고 → 질문에 답하는 형태로 만듭니다.

brz — 원형 보존
있는 그대로
원천 시스템 테이블을 손대지 않고 받아 보관. 나중에 무엇이든 다시 만들 수 있는 안전한 원본.
→
slv — 정제·표준화
깨끗하게 정리
중복 제거 + 최신판만 남기고, 이름·형식을 표준화. 비즈니스 판단은 아직 넣지 않음.
  • 같은 건의 여러 버전 → 최신 1건만
  • 원천값 원형 유지
→
gld — 비즈니스 마트
질문에 답하는 형태
차원을 붙이고 비즈니스 규칙을 적용한 공식 마트. 컨슈머가 바로 쓰는 결과물.
  • dim_ 무엇인가(기준정보)
  • fct_ 무슨 일이 있었나(사건)
brz 원형 slv 정제 gld 마트

모델 1개 = 흩어졌던 로직을 모아 담은 단일 정의(SSOT)

엑셀·파이썬에 흩어져 있던 계산을 SQL 파일 하나로 옮기고, 파일 머리말에 "이 값이 무엇이고 어떤 레거시 로직을 그대로 승계했는지"를 적었습니다. 정의·설명·검증이 한곳에서 끝납니다.

-- 정산 품의(settlement) 표준화 — 레거시 xcl_settlement_update.sql 의 latest-version 디덥 승계.
-- 원천값 보존(명칭 원형 유지), 비즈니스 판단 없음. (siteid, settlement_wono) 당 최신 1행만 남긴다.
with ranked as (
  select *,
    row_number() over (
      partition by siteid, settlement_wono
      order by mod_dt desc, data_ver::int desc   -- 최신판이 이긴다
    ) as rn
  from {{ source('brz_ems', 'ems__xcl_settlement') }}
)
select ... from ranked where rn = 1    -- slv 규칙: view 로 산출

"규칙 변경 없음(레거시 이식)"이 원칙입니다 — 검증되어 온 계산은 손실 없이 옮기고, 흩어져 있던 사실만 하나로 모읍니다.

04지금 무엇을 쓸 수 있나 — 마트 카탈로그

최종 결과물인 gld 마트는 4개 비즈니스 도메인으로 정리돼 있습니다. 각 마트가 "어떤 질문에 답하는가"로 읽으시면 됩니다.

도메인마트어떤 질문에 답하나
정산
settlement		 fct_settlement정산 품의별 금액·상태·협력사·지급일은?
fct_settlement_detail정산 상세(기타지원금 원천) — 라인별 비용 내역은?
dim_xcl_taxobject세금계산서 발행 대상과 예산구분은?
예산
budget		 dim_budget_code수선비(PCS) 예산 코드 체계는?
dim_pcs_budget_code코스트센터·회계월별 대표 예산구분(division)은?
PCS 리스트
pcs_list		 dim_xcl_pcs_list레거시 4개 산출물을 통합한 PCS 리스트 정본은?
fct_xcl_pcs_list_etccost기타지원금(8개 비용을 펼친 행)은?

이름이 곧 사용법입니다. dim_은 무엇인가(설비·예산·대상 같은 기준정보), fct_는 무슨 일이 있었나(정산·비용 같은 사건). 앞의 도메인 폴더로 관심 영역을 먼저 좁히면 됩니다.

05믿을 수 있는 이유 — 품질과 정본 회수

엑셀이 정본이던 자리를 시스템이 되찾으려면, 시스템 값이 더 믿을 만해야 합니다. 그래서 값이 만들어질 때마다 자동으로 검증합니다.

2층
품질 검증 (컬럼 + 복합키)
9
복합키 유니크 검증
1곳
회계달력 단일 정의
차단
검증 실패 시 하류 중단

이중 방어 — 검증이 통과해야 흐른다

기본 검증(빈 값 없음·허용값·참조 무결성)에 더해, "한 건이 정말 한 줄인가"를 보장하는 복합키 유니크 검증 9종을 slv·gld 양쪽에 걸었습니다. 하나라도 실패하면 그 아래 단계로 나쁜 데이터가 흐르지 않습니다.

회계달력을 한곳으로

사람마다 다르던 회계연·월·주 계산(16일 경계)을 공용 매크로 하나로 통일했습니다. 이제 모든 마트가 같은 규칙으로 기간을 셉니다.

before / after — 회계 기간 계산

AS-IS · 파일마다 복사·변형된 CASE

-- A씨 엑셀   if(day>=16, month+1, month)
-- B씨 쿼리  case when ... -- 미묘하게 다름
-- C씨 파이썬 dt.month -- 경계 처리 누락

TO-BE · 공용 매크로 재사용

{{ fiscal_year(cre_dt) }}
{{ fiscal_month(cre_dt) }}   -- 16일 경계 내장
{{ fiscal_week(cre_dt) }}
정본 회수. 엑셀의 정확성을 SQL로 흡수하고 레거시 산출물과 대사(검증)한 뒤, 공식 마트가 유일한 소비 원천이 됩니다 — 개인 엑셀로 되돌아갈 이유가 사라집니다.

추적 가능성

"이 리스트의 이 금액은 어느 정산 건, 어느 원천 테이블에서 왔나?"를 그래프로 되짚을 수 있습니다. 흩어진 엑셀에서는 불가능했던 일입니다.

손이 아니라 이벤트로 도는 흐름

원천 추출이 끝나면 변환이 자동으로 연쇄됩니다. 매번 사람이 엑셀을 열어 다시 계산하던 반복 작업이 사라집니다.

07선행사례가 남긴 것 — 다른 팀·소스로

이 구축은 재현 가능한 패턴입니다. 한 팀이 먼저 걸어 검증한 길이라, 다른 도메인·소스도 같은 방식으로 얹으면 됩니다.

소스 추가 = 선언 1블록

새 원천 시스템을 붙이는 일은 설정 블록 하나 추가로 끝납니다.

마트 추가 = SQL 1개

모델 파일 하나를 두면 검증·계보·자동 실행에 스스로 편입됩니다 — 나머지는 자동.

1인 운영 가능한 구조

사람이 많이 필요하지 않은 자동화된 구조. 이 팀이 그것을 실증했습니다.

현재는 단일 소스 ems로 시작했지만, stg_<소스>__엔티티 명명과 slv/<소스> 폴더 규칙으로 다중 소스 확장이 이미 준비되어 있습니다. 다음 소스는 이 선행사례를 그대로 따라 얹으면 됩니다.

한 줄 요약 — 흩어진 개인 엑셀 → 검증되는 공식 마트. 신뢰가 회복되면 사람들은 시스템으로 돌아오고, 악순환은 선순환으로 바뀝니다.
